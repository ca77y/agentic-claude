# agentic-slop toolkit for Claude Code

One plugin, `slopify`, provides seven workflows and five skills for engineering and library work. Each workflow script is the only orchestrator of its run: it gathers evidence through scouts, takes judgement from advisors, produces through the writers and `coder`, validates through lenses and `qa`, and acts on the board and forge only through `pusher`.

Scouts, lenses, and advisors have one task each, and the workflow passes the schema they return. Dispatch names are plugin-qualified, such as `slopify:scout-code`.

## Fresh verdicts

`qa`, `library-clerk`, and every lens carry the same Report-only contract: judge only work you didn't produce or judge before, and only the revision the brief names, or a digest of what you judged when it names none; change nothing; report a check that couldn't run as unverified; pass only when every required check ran and nothing blocking remains. Every verdict is a new agent dispatch made after the revision it judges exists, never a continuation of a producer or an earlier validator. Validators never repair the candidate; the producer fixes from the findings, and new validators judge the new revision.

In delivery's outer loop, a problem counts only once `judge` confirms it. `judge` says what kind of problem it is, and the script sends it to whoever can act on that kind. Only a confirmed `blocker` or `major` starts a fix round: `coder` fixes code and tests, `writer-spec` the spec, `writer-docs` documentation, and a spike's or research run's own writer its document. A round that runs also applies the confirmed `minor` problems its writer can fix. A check that couldn't run or left no proof is listed for a human, never sent to a producer. Each loop has a round cap, and a loop that runs out records what is open and the run continues; see [`docs/DESIGN.md`](docs/DESIGN.md).

## Blocked results and reruns

`deliver-story` returns `ready` or `draft`, and stops early only on the halt conditions in [`docs/deliver/STORY.md`](docs/deliver/STORY.md): `not-started` when the card can't be read or isn't `Deliverable`, and `blocked` otherwise, even after the PR exists; decisions the run made that a person should confirm are listed under **Needs you** in the PR description. When any other workflow can't proceed — a prerequisite is missing, an agent doesn't return, or a push or board operation fails — it returns `blocked` with the step, what it needs, the steps completed, the checkpoints that exist, and how to rerun. A run that can't start, such as one given a card with open questions, returns `not-started` saying what to fix, and `deliver-bugfix` returns `unreproducible`, with the card labelled, when it can't reproduce the bug. A story that needs changing goes back through `shape`; the deliver workflows never rewrite a story or a criterion's meaning.

A rerun is a new run with fresh budgets:

- **In the same session, for a decision**, rerun with the same args plus `answers`, a map from each decision id in the `draft` result to its answer, such as `{"q1": "a"}`, and you may pass `resumeFromRunId` to replay unchanged steps from the cache. Each answer is plain text: a string, a number, or a boolean. A delivery or `research` run given `answers` that isn't a map, or an answer that is an object or a list, returns `not-started` before any agent works, naming what to fix; a `null` answer counts as unanswered. Every `coder` and `judge` in the rerun gets the answers. A `blocked` result's `rerun` text says to fix what each need names and rerun without resume; a need that names an arg, such as a missing story, is answered in that arg. `shape` takes no `answers`: answer its open questions on the card and run it again.
- **Across sessions, or after the story or repository changed**, rerun without resume. Each delivery and `research` run starts by asking `scout-checkpoint` for its durable checkpoints — the branch and worktree, the PR, the committed spec, and the ledger's checkpoint lines, which record a confirmed reproduction, committed findings, and finished rounds — and skips every step a current checkpoint proves complete. A `shape` rerun on a card labelled `Shaped` skips Ground and Advise. A checkpoint value counts only in its expected shape, never as prose, and a `shape` draft for an idea with no card is named from its text plus a short hash of the whole text, so two ideas that open alike never share a file; every other run names its files from its card. A delivery with a PR resumes at the review, and one whose ledger shows a finished round doesn't rebuild the spec's tasks: it goes on with the next round, counted afresh against the round budget. A story whose ledger shows its spec committed skips the design, advice, decision, and spec stages, and runs only the challenge again when the ledger doesn't show it finished.

## Ledger

`deliver-story`, `deliver-trivial`, `deliver-bugfix`, `deliver-spike`, and `research` keep one append-only ledger per story worktree at `.tmp/ledger.md`. `pusher` is its only writer: each line rides on the `pusher` dispatch that makes its step durable, and only two dispatches just write the ledger: one records each review's outcome, and `deliver-story` records a finished spec challenge in a dispatch of its own, because a run halted in the build makes no later dispatch for the line to ride on. It records each run, `done board-start`, `done spec` (with a copy of the spec's `build.json` and `validate.json`, so a rerun reads the spec back from the ledger), `done challenge`, `done findings`, a bug's `reproduced` line, `done round`, and `done publish`, each review's trigger and outcome, `delivery ready` or `delivery draft` at the end, and a progress entry for each round's findings, rulings, attempts, and changes. Progress entries stay local: `pusher` never posts one, or any other ledger line, to a PR, a comment, or a card, and a rerun never reads one as a checkpoint. `writer-pr` reads them to see what is still open. `shape` needs no ledger; its checkpoints are its artifacts.

## Build and validate loop

Delivery runs two nested loops. In the inner loop, a `coder` writes a failing test, which is committed, a fresh `coder` makes it pass without touching that test, and a fresh `qa` validates the change and its history, so a fix that changed the test is caught. `writer-docs` then updates the documents the spec lists, against the code as built. The outer loop checks the whole story. `checks`, `validator`, and `lens-docs` run, one `judge` rules on every problem they report, confirming each with a severity and a kind, dismissing it, or leaving it unverified, and one gateway `judge` checks the round for anything missed. `writer-pr` then writes the PR's description whole, for the person who reviews it, and a mechanical check of its headings, length, and leaks sends it back when one fails. `pusher` pushes, even when something is still flagged, posts the description unchanged, and keeps the PR a draft when something is open. The description has four parts in this order: **What changes**, **Needs you**, **Why trust it**, and **Not done**.

The PR opens once nothing blocks, or on the last round either way. From then on each round also waits for the review that [`docs/FORGE.md`](docs/FORGE.md) declares, which runs when the PR opens and again whenever pusher requests it. `watcher` reads its findings, and `judge` rules on each one. Each open `blocker` or `major` that needs code starts the next round as its own inner loop, and one that needs documentation goes to that round's `writer-docs`. The outer loop runs at most three fix rounds and stops early when nothing improves. A clean review marks the PR ready and performs the board operations `docs/BOARD.md` declares for a clean review, such as moving the issue to In Review. Otherwise the PR stays a draft with each open item listed under **Not done**.

## Project authority

Project authority lives in [`docs/BOARD.md`](docs/BOARD.md), [`docs/FORGE.md`](docs/FORGE.md), `TESTING.md`, and `library/_meta/librarian.md` in the target project. Invoking a deliver workflow or `research` authorizes the story branch and worktree, attributable commits, the pushes each round makes, opening or updating the task's PR as a draft or ready, the declared review trigger, one issue comment when the run ends or halts, and filing the issues it lists. `deliver-spike` also authorizes creating, and then deleting, its own unpushed prototype branch and worktree, named by the "Spike prototypes" line of `docs/FORGE.md`; when that line says "none", it builds no prototype and lists what it couldn't measure under Unknowns. Invoking `shape` authorizes filing one card, or updating the card it was given or marking it a duplicate, and setting its `Shaped` and `Deliverable` labels. No workflow merges or releases. Every workflow and skill assumes the project is bootstrapped; rerun `bootstrap` to verify and fix the setup.

## Install

```bash
claude plugin marketplace add ca77y/agentic-claude
claude plugin install slopify@agentic-slop
```

Run `/reload-plugins`, or start a new session, after installing or updating to load skills, workflows, and agents.

Every workflow runs only when invoked explicitly: as `/slopify:<name>`, such as `/slopify:deliver-story SPR-12`, or when you ask to run the slopify `<name>` workflow. This includes `shape`, which no longer runs when you merely describe shaping work. The skills also run only when invoked, by qualified name such as `/slopify:ask`.

The workflows dispatch many background agents that run git, tests, and the forge CLI, so they are designed for auto-approve or bypass permission mode; in default mode those agents' permission prompts arrive while the workflow is waiting.
