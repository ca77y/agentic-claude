# agentic-slop toolkit for Claude Code

One plugin, `slopify`, provides nine workflows and three skills for engineering and library work. Each workflow script is the only orchestrator of its run: it gathers evidence through scouts, takes judgement from advisors, produces through `writer` and `coder`, validates through lenses and `qa`, and acts on the board and forge only through `pusher`.

Scouts, lenses, and advisors have one task each and no return format; the workflow passes their schema. Dispatch names are plugin-qualified, such as `slopify:scout-code`.

## Fresh verdicts

`qa`, `library-clerk`, `auditor`, and every lens carry the same Report-only contract: judge only work you didn't produce or judge before, and only the revision the brief names, or a digest of what you judged when it names none; change nothing; report a check that couldn't run as unverified; pass only when every required check ran and nothing blocking remains. Every verdict is a new agent dispatch made after the revision it judges exists, never a continuation of a producer or an earlier validator. Validators never repair the candidate; the producer fixes from the findings, and new validators judge the new revision.

In delivery, a problem counts only once `judge` confirms it. `judge` says what kind of problem it is, and the script sends it to whoever can act on that kind. Only a confirmed `blocker` or `major` goes back to a producer: `coder` for code and tests, `writer` for documentation. A check that couldn't run or left no proof is listed for a human, never sent to a producer. Each loop has a round cap, and a loop that runs out records what is open and the run continues; see [`docs/DESIGN.md`](docs/DESIGN.md).

## Blocked results and reruns

`deliver-story` returns `ready` or `draft` whenever a PR exists, and `blocked` only on the halt conditions in [`docs/deliver/STORY.md`](docs/deliver/STORY.md); open questions become recorded assumptions in the PR. When any other workflow can't proceed — a gate runs out of failures, a decision is open, the story is unbuildable as stated, or a prerequisite is missing — it returns `blocked` with the step, what it needs, the steps completed, the checkpoints that exist, and the attempts. A story blocker goes back through `shape`; the deliver workflows never rewrite a story or a criterion's meaning.

A rerun is a new run with fresh budgets:

- **In the same session, for a decision**, rerun with the same args plus `answers` for each decision, and pass `resumeFromRunId`. Steps before the one that raised the decision replay from the cache. A decision's id comes from its question, and the producer that raised it is given each answer beside its question. The `rerun` text offers resume only when every need is a decision; for any other need, fix what it names and rerun without resume. Answers to an `input` need, such as `reproduce-bug`'s request for more detail or a writer's blocker, go under `answers.<id>` too and reach the writer that raised it (a writer's blocker, from the first dispatch of the rerun); an input need that names an arg, such as a deliver workflow's missing story text, is answered in that arg. A filed `shape` draft is not validated or revised again.
- **Across sessions, or after the story or repository changed**, rerun without resume. Each run starts by asking `scout-checkpoint` for its durable checkpoints — the branch and worktree, the committed spec, ledger lines, the PR, a draft, a findings document, a filed card, or a reproduction directory — and skips every step a current checkpoint proves complete. A checkpoint value counts only in its expected shape, never as prose, and a draft, reproduction, or spike is named from its idea text plus a short hash of the whole text, so two ideas that open alike never share a file. A delivery with a PR resumes at the review, and one whose ledger shows a finished round doesn't rebuild the spec's tasks.

## Ledger

`deliver-story`, `deliver-trivial`, `deliver-bugfix`, and `review-pr` keep one append-only ledger per story worktree at `.tmp/ledger.md`. `pusher` is its only writer: every `pusher` dispatch appends the lines for the step it makes durable, so no dispatch exists just to write the ledger. It records each run, `done spec`, `done round`, and `done publish`, and each review's trigger and outcome. `shape`, `deliver-spike`, and `reproduce-bug` need no ledger; their checkpoints are their artifacts.

## Build and validate loop

Delivery runs two nested loops. In the inner loop, a `coder` writes a failing test, which is committed, a fresh `coder` makes it pass without touching that test, and a fresh `qa` validates the change and its history, so a fix that changed the test is caught. `writer` then updates the documents the spec lists, against the code as built. The outer loop checks the whole story. `checks`, `validator`, and `lens-docs` run, one `judge` per problem confirms it with a severity and a kind, dismisses it, or leaves it unverified, and one gateway `judge` checks the round for anything missed. `pusher` then pushes, even when something is still flagged, records what is open in the PR, and keeps the PR a draft.

The PR opens once nothing blocks, or on the last round either way. From then on each round also waits for the review that [`docs/FORGE.md`](docs/FORGE.md) declares: the Claude Code Review GitHub Action, which runs when the PR opens and again on each `@review` comment. `watcher` reads its findings, and `judge` rules on each one. Each open `blocker` or `major` that needs code starts the next round as its own inner loop, and one that needs documentation goes to that round's `writer`. The outer loop runs at most three fix rounds and stops early when nothing improves. A clean review marks the PR ready and moves the issue to In Review. Otherwise the PR stays a draft with each open problem and its outcome listed. Invoking `review-pr` on a PR enters the same loop.

## Project authority

Project authority lives in [`docs/BOARD.md`](docs/BOARD.md), [`docs/FORGE.md`](docs/FORGE.md), `TESTING.md`, and `library/_meta/librarian.md` in the target project. Invoking a deliver workflow or `review-pr` authorizes the story branch and worktree, attributable commits, the pushes each round makes, opening or updating the task's PR as a draft or ready, the declared review trigger, one issue comment when the run ends or halts, and filing the issues it lists. `reproduce-bug` authorizes filing one `Bug` card. `deliver-spike` authorizes creating, and then deleting, its own unpushed prototype branch and worktree, named by the "Spike prototypes" line of `docs/FORGE.md`; when that line is missing or says "none", it builds no prototype and names the gap among its open unknowns. Its findings document stays uncommitted. `shape` files or updates the story card only when its args set `file: true`. No workflow merges or releases. Every workflow and skill assumes the project is bootstrapped; rerun `bootstrap` to verify and fix the setup.

## Install

```bash
claude plugin marketplace add ca77y/agentic-claude
claude plugin install slopify@agentic-slop
```

Run `/reload-plugins`, or start a new session, after installing or updating to load skills, workflows, and agents.

Every workflow runs only when invoked explicitly: as `/slopify:<name>`, such as `/slopify:deliver-story SPR-12`, or when you ask to run the slopify `<name>` workflow. This includes `shape`, which no longer runs when you merely describe shaping work. The skills also run only when invoked, by qualified name such as `/slopify:ask`.

The workflows dispatch many background agents that run git, tests, and the forge CLI, so they are designed for auto-approve or bypass permission mode; in default mode those agents' permission prompts arrive while the workflow is waiting.
