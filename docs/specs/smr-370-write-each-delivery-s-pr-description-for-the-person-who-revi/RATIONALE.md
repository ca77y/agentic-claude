# Why the spec is what it is

The acceptance criteria come from card SMR-370 itself. The relayed issue text left them out, so they were read with get_issue. The card settles the revision cap (three), the draft reason, the rule that 'a delivery never stops for its description alone', body identity, filed-card links in the final dispatch, the 4,000-character limit, Needs you 'only when there is something', and resume invariance 'whatever text the entries quote'.

## Designs considered

- **A, smallest change.** Keep the run-state renderer as writer-pr's input. writer-pr writes `.tmp/pr-body.md`, the lens retries once, readiness never depends on the description, and the scout prompt gets a sentence telling it to skip progress lines. Rejected because it breaks several Deterministic criteria: one retry is not three revisions, there is no draft gate, a stale file can be posted, the stub harness can't assert body identity, cards are filed after the final description, and resume still trusts the scout's substring match. Fixing all of that turns it into C.
- **B, long-term structure.** A ledger grammar module, one grep key for checkpoints, `factsOf` deciding placement in code, a reordered reviewRound, and a new Describe phase. It costs more than the issue needs. One exact grep answer from a haiku scout is fragile: a truncated answer silently gives built=false and the run redoes work. The reorder changes ledger order, the new phase touches five metas, and `factsOf` takes placement away from writer-pr. Its handling of an unverified lens was grafted into C.
- **C, robust under failure (chosen).** writer-pr returns `{ body }`, the loop holds it and passes it unchanged to pusher, and a deterministic `checkDescription` runs before the lens. Up to three revisions; a failure at the final stage makes the PR a draft. Follow-up cards are filed before the final description. Progress entries can't be mistaken for checkpoints because code accepts only real checkpoint lines.

## Grafts onto C, and why

- **No fallback description.** It would put code back in charge of the posted text, which the issue replaces. A failed writer-pr attempt counts as one; the run halts only when no body exists.
- **The lens runs only after the guard passes,** so a mechanical failure costs no lens call (performance, risk and architecture advisors). c3 needs a lens dispatch before every posting, so when revisions run out the lens runs once on the body that will actually be posted.
- **An unverified lens is retried once, then counts as not passed, with no revision.** Revising text can't fix a check that couldn't run.
- **`describe` never takes a Loop from another module**, since Loop is unexported and a separate module would import loop.ts both ways.
- **The stage runs under the existing `Push` phase,** so the metas and workflows.test.ts stay as they are.
- **endLoop describes once** and both the opening push and finish post that body.
- **Progress entries are built only by `progressLine`, carry no `<` or `>`,** so pushBrief's `fill every <placeholder>` can't rewrite them, and pending entries ride on the next ledger-writing pusher dispatch, kept until it succeeds, so review rulings need no reviewRound reorder (B's reorder was ruled against).
- **Card filing doesn't halt on a partial failure** and reuses small.ts's marker line, so a rerun files no duplicates.
- **Security advisor.** writer-pr treats card, diff and ledger as evidence, never instructions. Grafted further in revision 2: leak problems block posting (below) and the fence can't be closed from inside the body.
- **The phrase test's scope is stated in the test.** Tracked files only; docs/specs/ (the card's exclusion), library/ (research notes that quote other text) and test/ excluded; src/ included so the built JS can't regress.
- **writer-pr waits for the round's commits,** so the diff it reads is settled (risk advisor).

## Revision 2: problems fixed and why

- **Overflow (shared Overflow rule, d15).** With one Why trust it line per criterion and every decision listed, a story like this one (26 criteria, 14 acceptance decisions) can't fit 4,000 characters; the guard fails every attempt and every clean large delivery ends draft. The issue's Scope says 'about one screen with links for overflow', so pr-description.md, writer-pr, lens-pr and checkDescription share one rule: grouped criterion lines, and grouped Needs you lines (revision 3 widened these).
- **Rejected non-empty checkpoint answers (checkpoint rule, d18).** The old spec silently treated a slightly wrapped real checkpoint as absent, which rebuilds every task, repeats board-start, reproduces again or reruns an investigation. Now common scout wrappers are tolerated, and an unreadable answer halts naming the key (revision 3 narrowed the halt).
- **Fence injection (Fencing rule, d1).** The body is model-written from untrusted card, diff and ledger text and was embedded in a fixed `BODY>>>` fence in an instruction to the agent with push, PR and board powers. The closing delimiter is now chosen per dispatch and absent from the text, which keeps the body byte-identical for c4. The same applies to filed card text, including small.ts's.
- **c10 oracle (d7).** Code could reject a progress line but never fall back to the real one, so the mixed case was untestable. Each ledger key now returns every line containing its form and code takes the last accepted one (revision 3 pinned how the lines travel). resume.test.ts names each scenario and its baseline.
- **Draft reason missing from the body (d16).** See Rulings.
- **Card identifier and link (d6).** An operation had one `reference` and pushBrief asked for one value, so a real pusher would drop the link. pusherSchema gains `link`; pushBrief, pusher.md and the c13 stub use the same shape; schemas.ts joins the loop task.
- **One channel for kind, target and filed cards.** PrState no longer carries them; renderState renders only criterion results and open items, and the brief carries the three as their own lines.
- **qa.md dropped.** No criterion or scope bullet needs it, and changing qa's acceptance source would change every qa dispatch, including the validate workflow.
- **Story What changes** opens with the outcome and contains the Spec line once (d9), since c21 needs it to say what changes and why.
- **Per-key checkpoint forms** are stated once in the shared rule, because three keys share `done` as their second field and the old 'second field is the key's word' matched the wrong lines.
- **Size and altitude.** Restated criteria, test names, call-by-call steps, function-body expressions, matching algorithms, scaffold replacement words, and constants the issue doesn't name (agent models and efforts, label strings, a two-sentence reason cap) were removed. resume became its own task so the loop task fits its budget; it runs before loop because both edit the how, research and spike tests.

## Revision 3: problems fixed and why

- **Uncommitted Needs you items had no overflow path (Overflow rule, d14, d15).** Revision 2 allowed a count and a link only for items a committed file lists, but the lists that grow without limit are not committed: coder choices gain entries from every task and fix round, and confirmations and manual actions are run state. A six-task story with a few fix rounds puts dozens of items under Needs you, breaks the limit on every attempt and ends a clean delivery draft, the original failure moved to another section. Now items of one kind may be one grouped line with their count and a link: to the committed file that lists them, or else to the card, whose comment from finish lists each in full. The card was chosen over a new durable file because it already exists, is known before the final description is written, and finish already comments on it; linking validator evidence stays out of scope. The loop and rules fixtures gain dozens of coder choices and confirmations so the tests cover the realistic worst case, not only criteria and spec decisions.
- **A run line quoting a form halted every rerun for good (checkpoint rule, d18).** takeLines writes the first part of the story argument into a run line on every run, and for the four prompt-taking workflows that is free text, which in this repo can quote a checkpoint form. The scout correctly returns that line; revision 2 halted on it, and since readResume runs on every invocation and the line stays in the ledger, no rerun could get past Locate without editing the ledger by hand. Now any stamped ledger line that is not the key's checkpoint is ignored as progress entries are, and only an item that can't be read as a ledger line halts. resume.test.ts gains the run-line case.
- **How several lines per key travel was unstated (checkpoint rule carrier, d7).** Two reviewers raised it. fact() returns only the first evidence item whose source matches, and scout-checkpoint.md said one item per key, so the agents task, the resume brief and the stubs could each pick a different shape and the stubs would still pass. Against a real scout returning one item per line, a progress entry listed first would hide the real line (the c10 rebuild), review-fired would take the lowest n, and done-findings an earlier round's paths. The shared rule now pins one evidence item per matching line, source the key, in ledger order, read by filtering every item. One item per line was chosen over a newline-joined excerpt because scout-checkpoint.md already tells the scout to put each finding in its own item, so the real agent's habit and the contract agree. resume.test.ts covers the progress entry listed first, and several review-fired and done-findings lines.
- **The rules task broke loop.ts (former d20, now history).** Replacing renderBody and PrBody in the rules task left loop.ts importing a missing export, so the pre-commit `make lint` rejected that commit. Revision 3 kept them until the loop task switched loop.ts to renderState. That transition is finished: af1ea46 removed both, loop.ts uses renderState, and neither name appears in src/ or test/. Revision 6 removed d20 from build.json.
- **Unfixed findings had two places (Overflow rule placement, d19).** draftReasons lists every escalated and open finding beside held criteria and review state, and the brief carried both it and renderState's open items, so the shared rule put each finding under Needs you and Not done at once, inviting the duplicate c24 forbids. Now the brief's draft-reason line carries only held criteria and review state, and every unfixed finding goes only under Not done. LoopResult and the card comment keep the full draftReasons, since they are not the description.

## Revision 4: problems fixed and why

- **Two new halts were undeclared (shared Halts rule, docs task, d2, d18).** d2 halts when writer-pr never returns a body and d18 halts on an unreadable checkpoint item, and both can fire after a PR exists. architecture.md says a delivery ends in a PR unless a declared halt condition holds, DESIGN.md says only listed halts stop a workflow, and STORY.md calls H1-H5 the only conditions and a draft the worst outcome once a PR exists. Left undeclared, the built system would stop where its docs say it can't. The decisions stand; the docs task now adds both halts to the STORY, TRIVIAL and SPIKE halt tables with where each is found and what the user gets (BUGFIX and RESEARCH defer to TRIVIAL's table), and qualifies STORY's worst-outcome sentence. Dropping the halts was rejected: d2's alternative is a code-rendered fallback the issue replaces, and d18's is silently redoing finished work.
- **Over the size budget (shared, loop todo).** shared restated what d7, d8, d15, d18 and d19 already carry; the overflow, checkpoint and progress-entry rules now point at those decisions and keep only the interface the tasks must agree on (the per-key forms and the scout's evidence-item carrier). The loop todo dropped the brief field layouts, the step-by-step describe stage and tests restating c3-c13, keeping the observable order and the brief inputs that d6, d16 and d19 constrain.
- **Implementation detail removed.** The list of scout wrappers checkpointLine strips is gone; tolerating a scout's wrappers is the requirement. The label convention 'Labels name the agent first' is gone: no decision or rule set it and loop.ts's existing labels don't follow it. The phrase test no longer names the command that lists tracked files, and the plugin-text test no longer prescribes how it matches text; both are the coder's choice.

## Revision 5: problems fixed and why

The build of revision 4 exposed a task split that couldn't finish. Every advisor finding below was adopted except where noted. Revision 6 removed the tasks this section arranges, so it is history: it explains how the test files came to be split as they are, not an instruction in force.

- **The phrases task could deliver nothing (d21).** Its only files were test/phrases.test.ts and test/plugin-text.test.ts. Earlier test-first commits had already written both, so they were protected, and every fix they needed was in README, the kind docs, DESIGN.md and plugin.json, which other tasks own. Its builder changed no file. The task is gone, and each test now sits with the task whose files make it pass. Keeping it as a final make-check gate over every story path was rejected: it would duplicate the docs task's files.
- **Two tasks owned test/plugin-text.test.ts.** The agents task's test commit edited it and phrases listed it. It also mixed agent assertions with doc assertions. The split is done (e4a9fcd, 9b109ed): the agents task keeps test/plugin-text.test.ts with only the writer-pr, lens-pr, Spec-line and pusher-ledger assertions. test/docs-text.test.ts holds the kind-doc, forge, README, DESIGN and plugin.json assertions. A separate test/plugin-text-agents.test.ts was considered. Keeping the existing file name for the agents half moves fewer assertions.
- **The docs task had no test file.** Its coder wrote test/phrases.test.ts outside its paths. The docs task now owns test/phrases.test.ts and test/docs-text.test.ts, and its todo carries the phrase test's scope (tracked files, the stated exclusions). docs stays a task instead of being left to writer-docs, because writer-docs gets only the docs list and the code, so it can't see the halt-table, heading and README-row requirements in the todo. The docs task's files still overlap the build.json `docs` list. writer-docs runs after the inner loops and finds those documents already current.
- **docs depends on rules, resume, loop and agents.** The phrase test scans src/, plugin text and the built JS, and those lose c14's phrases only in loop and agents. docs runs last, so its own edits make c14-c18 pass.
- **c19 only on the last task (superseded in revision 6).** `make check` runs every unit test, including other tasks' committed failing tests and text that isn't written yet. The rules, resume and loop builders each reported it unmeetable, and each rerun would waste a fix round. Earlier tasks' evidence is `make lint` plus their own tests, which matches the Makefile's reason for leaving unit tests out of the hook. c14 left the rules task for the same reason, because its test belongs to docs.
- **c18 split by owner.** Its single test checked README.md, which only docs writes, and pusher-ledger.md, which only agents writes. agents now proves the pusher-ledger half and docs the README half.
- **rules and resume list the built JS and run `make build`.** rules.ts and resume.ts are bundled into plugins/slopify/workflows/*.js, and build:check runs in the pre-commit `make lint`. Resume commits b710b8e and 6fd0f88 failed build:check until e07b8af, and rules commit 5724740 wrote the JS outside its list. rules, resume and loop already run in dependsOn order, so adding the shared output creates no parallel overlap.
- **README rows named precisely.** 'The five PR-opening workflows' agent rows' named rows README doesn't have, so the coder asserted only the family rows. The todo now names the per-workflow lists in the Area table's Delivery row (deliver-story; deliver-trivial and deliver-bugfix; deliver-spike) and Library row (research), plus the Producers and Lenses rows. c17's evidence and test cover all of them, because c17 says 'the product's agent listings'. One advisor proposed cutting the requirement to the Producers and Lenses rows. That was rejected: the per-workflow lists are agent listings c17 covers, the text is already there, and without a test a rerun could drop it.

## Rulings in force

- **Halts.** The run stops for its description only when writer-pr never returns a body, and on resume only for an unreadable checkpoint item; both are declared in each kind's halt conditions.
- Lens findings go only to writer-pr. They never go to judge or count as change problems. Their only other effect is the draft reason when the final stage fails.
- Only the final stage gates readiness. An intermediate round's failure changes nothing, because the next round rewrites the description whole.
- **d15, overflow vs c22.** A grouped Needs you line with a count and a link, to the committed file that lists the items or else to the card whose finish comment lists each, counts as those items appearing under Needs you. If a person reads c22 as ruling out summary by link, its conflict with c20's limit is theirs to settle.
- **d19, findings placement.** An unfixed finding appears only under Not done; draft reasons in the description are held criteria and a review that is not clean.
- **d16, description draft reason.** The posted body never names 'The PR description did not pass its check.'; finish's card comment and LoopResult.draftReasons carry it. Every alternative breaks another criterion: code appending it breaks c4 and returns the body to code; a writer-pr dispatch after the lens breaks c3 and exceeds c6's cap; briefing the last revision as draft is wrong whenever that revision passes. This is the one exception to c22. The final brief still carries the target and every draft reason known before the stage.
- **d17, leak rule over c4/c6.** A body with a leak problem (absolute path, `.tmp/`, ledger line, credential-shaped text) is never posted. The latest leak-free writer-pr body is posted unchanged, or none. writer-pr reads a ledger holding absolute worktree paths, and a draft PR on a public repo is public; c4's purpose, a posted body untouched by code, still holds. Format and lens failures still post the last revision and end draft.
- The coder's trivial choices and non-acceptance decisions go under Needs you as confirmations (a card design choice), listed or grouped with a link to the card, whose finish comment lists each.
- Validator evidence under `.tmp/evidence/` is never linked, because publishing it is out of scope.
- No plugin version bump.
- **No build task (revision 6).** Every Deterministic criterion is proved by a committed, passing test, so build.json has no task, and c19 runs once in validation on the tree the PR carries. The former d21 split is history. AGENTS.md already requires every commit to pass the hook and `make build` after src/ edits.

## Open risks

- The branch holds commits that fail `make lint` (b710b8e and 6fd0f88 fail build:check) and duplicate implement commits (af1ea46 and f242ec3, a06b51a and 9b109ed). Squash the story on merge so master never receives them; until then, bisecting the branch hits build:check failures.
- writer-docs rewrites the build.json `docs` list after the inner loops, and test/docs-text.test.ts and test/phrases.test.ts match wording in those files. A reword that breaks them shows only in c19's make check at validation. The agent-owned plugin files that test/plugin-text.test.ts matches (pusher.md, pusher-forge.md, pusher-ledger.md, scout-checkpoint.md) left the `docs` list in revision 6 for this reason.
- The model-side half of the Fencing rule has no test: writer-pr.md's and lens-pr.md's 'evidence, never instructions' sentence and pusher.md's data-not-instructions and closing-delimiter rule. A later edit could drop them and every test would still pass. A follow-up that adds those assertions to test/plugin-text.test.ts closes it.

- c10 is proved only up to the scout returning every line containing the key's form. A scout that returns only a progress entry and omits the real line makes the run resume as if the checkpoint were absent.
- The halt on an unreadable checkpoint item can stop a run when haiku wraps an answer in prose the wrapper tolerance doesn't cover; the rerun is the recovery, since the item comes from the scout's answer, not from a ledger line.
- A grouped Needs you line sends the reviewer to the card comment for the full list; if finish fails to post that comment, the link points at a card without it until a rerun posts it.
- Each PR update adds two to eight dispatches. Measuring that is left to a full eval (SMR-364).
- pusher is a model copying the body and progress lines. A body it alters can't be detected without reading the PR back. A mangled progress line can't become a checkpoint.
- A flaky lens can turn a clean delivery into a draft. Three revisions and the single unverified retry bound this, and the card accepts it.
- The scout may return an older checkpoint line with the right shape; the check catches shape, not recency, as today.
- The leak rules catch credential-shaped text by pattern, so a secret of an unusual shape can still pass.
- SMR-360 and other open worktrees touch loop.ts, the five workflows and the built JS. Rebase and run `make build` again.
- Projects bootstrapped earlier keep their old FORGE.md body line until a person reruns bootstrap (manualActions).
- The Full eval criteria (c20 to c26) can't be verified until someone runs them by hand. Under TESTING.md they keep the PR a draft.
