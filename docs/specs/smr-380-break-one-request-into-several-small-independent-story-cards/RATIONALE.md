# Why the spec is what it is

The issue asks for one run of slopify to turn a larger request into a capped set of story cards. Each card must meet the story contract, be grounded, carry relations to the cards it depends on, and never duplicate a card already on the board. The spec builds this as a split mode of `shape` on the code as the coders find it. That code predates the criteria-count check (`MAX_CRITERIA`, `tooBig()`), and its `refine()` takes the first open questions as a list. An earlier revision told the coders to reuse `tooBig()`, which they cannot see. Split mode needs nothing from that check, so the spec no longer names it.

## Designs considered

- **A, smallest change that fits the existing patterns (chosen).** A split mode of `shape`: Ground once, plan once, then run the existing per-card steps (read, adviseAll, write, refine, file) for each part, filing one card at a time and never more than the cap. Every advisor judged it proceed-with-conditions, and each condition is a graft below.
- **B, best long-term structure.** Move the single-card pipeline into `lib/card.ts`, with set mode in `lib/card-set.ts`. Rejected: no criterion needs about fifteen functions moved out of a `shape.ts` that recent work changed, and moving them in the same diff that changes them makes a single-mode regression hard to review. Its set line names only the request, so on a rerun, whether a part is covered rests on advisor-fit choosing among up to 20 similar cards. Its advisor-scope revision loop, COVERAGE_SCHEMA, free-string scope parameter, and a Kahn sort that duplicates `waves()` add concepts the issue doesn't ask for. It also let a model-read cap exceed what the user authorized. Grafted from B: batches, `d.done`, the Create binding, and a separate planner agent.
- **C, most robust under failure.** Sequential, catching each part's halt, relation verify and repair, rerun heal, `partial` status. Rejected: `Halt` has no kind, so catching per part would repeat an H3 budget or stop halt, or a systemic H2, for every remaining part, against SHAPE.md's halt contract. The rerun heal writes relations onto cards the run didn't file, such as the hand-filed SMR-381 to SMR-401, beyond the issue's authorization ("up to the cap, and nothing more"). The `partial` status, repair dispatches, and `relation` op are machinery no criterion needs. Grafted from C: the request-scoped hidden line, refusing an invalid cap, the Create binding, the planner's `omitted` list, and word counts.

## Grafts and the reason for each

- **Hidden line per part = request slug + part key.** Two requests that both have a part called `shopping-cart` must not share a line, or the second would see itself as covered and file nothing.
- **selectParts is the only cap enforcer; writer-split plans uncapped.** An earlier revision also told the planner to stop at the cap. With both, covered parts used cap slots, because the planner had dropped the uncovered parts that would have filled them, so a rerun filed fewer than the cap while uncovered work remained. A part the planner truncated reached the report only if the model listed it under `omitted`, so the issue's "anything left out because of the cap is named" rested on the model. Now the planner reports `statedCap` as a field, code picks the first `cap` uncovered parts in dependency order, and every part past them is named as over the cap. Ordering by dependencies first means the cap cuts dependents, never the parts they depend on.
- **The cap arg wins; a stated cap can only lower the limit (security).** The request's own text is untrusted model input. A planner that reads "cap 50" must not authorize 50. meta.whenToUse tells the main session to pass the user's cap as `cap`. An invalid present cap is refused, not defaulted, because it is the authorization limit.
- **No attempts-counter test.** Filing goes through `pushed()`, which halts on any result that is not ok, so a create that returns done:false ends the run whatever a counter does. The earlier "done:false still uses a slot" test could not fail. What done:false does is now the test: it halts H2, Stopped names the cards filed before it, and a rerun finds by its hidden line any card that create made and files no second card. The never-more-than-the-cap guarantee comes from selection, which hands filing at most `cap` parts.
- **Order with `waves()` (architecture).** It already exists in `lib/rules.ts` and keeps forward edges. partsOf drops dependency keys that name no part, so orderParts only needs the cycle fallback. An earlier revision handled unknown keys in both places.
- **Draft a wave, then file it (failure).** An earlier revision drafted and checked every selected part before filing any. A 20-part run is hundreds of dispatches, and any null agent result or H3 stop before filing ended the run with nothing filed. A rerun then repeated the full cost, so a budget smaller than one run could never make progress. Now each bounded wave is drafted in parallel, holding its first Halt and rethrowing it after the wave (`parallel()` turns a throw into null), and then filed one card at a time in order before the next wave starts. Each finished wave persists through `d.done` and its hidden lines, and a dependency is filed before its dependents because the order is the flattened dependency order.
- **`d.done` per filed card.** A halt partway through then lists the cards already filed in `completed`, and a rerun finds them by their hidden lines.
- **Relations bound on Create only, `blockedBy` and `relatedTo`.** A split run only creates cards and never updates one, and each brief names one create, so an Update binding or `blocks` would be text nothing uses. It would also force every existing project to rerun bootstrap for that text. The Update line and its removal binding stay as they are.
- **A relation with no binding stops the create (failure).** Before, the pusher could create the dependent card and only then report the relation unmet. The run halted H2 after the card existed. A rerun found that card by its hidden line, counted the part as covered, and, since a split never updates an existing card, never recorded the relation. This happened on every dependent card on a board that couldn't bind relations, and on the issue's own Slopify project until bootstrap was rerun. Now the brief and pusher-board.md make the relation a precondition: pusher creates nothing and reports it unmet, and a rerun after bootstrap files the card with its relation. Bootstrap binds the tracker's relation on Create, or marks the operation unsupported, as its board reference already requires (never a guessed binding). On a tracker that can't record relations, the create-nothing rule halts the run before any dependent card exists. An earlier revision added a References-line fallback in the card body for that case. It was removed: a line in the body is not the issue's "relation between the cards", the only board evidenced (Linear, docs/BOARD.md) has blocking relations, and the create-nothing rule already gives the safe halt. c3 is checked on the fake board's `blockedBy` and on the Create binding text.
- **The create-nothing rule lives in pusher-board.md alone; the binding lives in docs/BOARD.md and the bootstrap template.** An earlier revision put the rule only in pusher-board.md in t1's todo, but its plugin-text test and c3's evidence checked docs/BOARD.md for the rule too, so they tested text no task writes. Writing the rule in both files would break the docs rule to state each rule once. The test sentence and c3's evidence now match the split: BOARD.md and the template carry the Create binding, pusher-board.md carries the rule.
- **A separate planner agent, writer-split.** It keeps writer-card's one role and avoids a plan file that nothing reads. Its output is typed (PLAN_SCHEMA), as plugin-code.md asks. Each `omitted` entry goes into the report.
- **Sanitized, unique part ids (security).** Model-chosen keys end up in draft paths and hidden lines.
- **Checked ids, with the scout pinned to bare identifiers (security and correctness).** A duplicateOf or overlaps id counts only when it appears in that part's scout-related-cards evidence. Before, it had to equal a `location` exactly, but nothing made the scout put the bare identifier there for an ordinary match. A live scout writing a URL or "SMR-381 (Backlog)" would have the real duplicate thrown away and a second card filed. That is exactly the live-board case for the hand-split SMR-381 to SMR-401, which carry no hidden line. Now the per-part brief and scout-related-cards.md require the bare identifier as `location`, and checkedId also accepts the id as a whole token inside a location. The plugin names no tracker, so no identifier format is hard-coded (d10).
- **Required-parts gate only in split mode (simplify).** In split mode it decides whether a card is filed. Single mode keeps its refine and writer schema, so its tests don't churn. `overlaps` is an optional field on FIT_SCHEMA rather than a second schema.
- **Parts reported as name plus word count, with 0 words rejected in code (testability).** This catches "present but empty". A test pins REQUIRED_PARTS to card-templates.md so the two can't drift.
- **Pure helpers in `lib/split.ts` (architecture).** Cap parsing, ordering, selection, id checking, and the report can be unit tested, and shape.ts stays one orchestration.
- **A run-level stated-cap test (testability).** The only run-level stated-cap test used to be 50, which the default of 20 already satisfies, so an implementation that ignored `statedCap` passed. A stated cap of 2 with four parts and no `cap` arg must give exactly 2 creates and name 2 as over the cap of 2.
- **Report without plan-edge or unrelated lists (simplify).** No criterion asks for them. A dependency that got no card is already named as left out with its reason, and dropping these fields shrinks the interface t2 and t3 share.
- **Shared block kept within its 600-word budget.** Removing the References-line fallback and the redundant "Update stays as it is" from the relation-binding entry brought `shared` under budget; the Update line staying unchanged is stated in t1 and above.
- **Spec trimmed to its level.** Earlier revisions carried the full pusher brief text, exact reason strings, a wave size, a draft path, parsing rules, and source line numbers. These are the coders' decisions, so the spec now states what each phase must achieve and the interfaces t2 and t3 share. A later revision removed the call order t3's todo still spelled out inside shape.ts (which helpers run in what sequence, how each filing is recorded, how a failed create halts). t3 now states outcomes: the plan comes before selection, selection applies the cap, each filed part is recorded so a rerun resumes, and a failed create stops the run as Stopped naming the cards filed before it. The shared split.ts interface stays the contract between t2 and t3.
- **Confirm the live relation write by hand (risk).** The issue asks for this before the relation criterion is built on it. It writes a real card, so it is a manual action, not a task.

## Rulings in force

- Split mode is selected by `split: true` and takes the request as `idea`. It refuses `card` (splitting an existing card is out of scope) and any kind but story.
- A split run never updates, relates onto, or marks an existing card. Covered parts are only reported.
- A part still missing a required part after the last revision is not filed and does not take a cap slot. Its slot is not refilled, because selection happens before drafting. So a run can file fewer than the cap while uncovered parts remain, and the report names them.
- A dependency whose part got no card records no relation. That part is named as left out.
- c4 (Full eval) cannot run here: the `make eval` target is under SMR-364, and the Cookidoo pages are in another project's library. It is reported cannot-verify, so the PR stays draft under TESTING.md. It must never run against the live board, which holds SMR-381 to SMR-401.

## Open risks

- Rerun stability depends on the planner reusing the same part keys. When keys drift, the hidden line misses and coverage falls to advisor-fit's judgement, which can file a near-duplicate on a live rerun. The deterministic tests cover both routes with stable stubs.
- Whether the live board records blockedBy on create is known only from the tool schema until the manual check is done.
- Cost: each part runs one scout, four advisors, the writer, and up to four check rounds. Grounding once and bounded waves limit this. A budget halt keeps every wave already filed, and a rerun skips those parts, so progress is made across reruns.
- writer-card's `parts` report is trusted the way its open questions are. lens-template still checks every draft as a second layer.
- If the planner leaves a whole-set constraint out of `constraints`, every card misses it. Only the Full eval run can show this.
- Projects bootstrapped before this change lack the Create relation binding. Their first dependent card stops the run before it is created, and a rerun after bootstrap files it (a manual action).
- If master's criteria-count check reaches the code before or during the build, single mode keeps it, and split mode's missingParts sits beside it in refine.
- The t3 todo is 313 words, over the 300-word task budget (t1 289, t2 249, t4 200). Cutting its sentence that the fake board records each card's blockedBy and relatedTo from the pusher brief would fix it, since t3's create entry for relation recording in `test/linear-board.ts` says the same; the test sentence that repeats validate.json's evidence could go instead.
- The part names are not fixed across tasks. writer-card's `parts` report (prompt in t1, schema in t3) and t2's REQUIRED_PARTS, which missingParts compares against, must agree, but the spec says only "each template part" and "the story template's required parts". card-templates.md's Story section requires Title, Summary, Why, Scope, Out of scope, and Acceptance criteria, while docs/BOARD.md keeps the title as a separate field and the summary as a paragraph with no heading, so a writer may leave Title and Summary out of `parts` or name them differently. Any mismatch makes missingParts flag those parts on every draft and no card gets filed. The fix is for the shared interface to list the exact names (card-templates.md's bold bullet names, Title and Summary included) and require writer-card to report them word for word, or to say how names are matched.
