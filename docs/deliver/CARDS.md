# Cards

What each delivery reads from a Linear issue, so that whatever writes the issue gives it everything the run needs. `shape` writes stories to this contract. The parts are encoded in the plugin's [card templates](../../plugins/slopify/references/card-templates.md), which each project's `docs/BOARD.md` maps to its issue store and `bootstrap` checks. A card in the project's own format holds these parts under the headings `docs/BOARD.md` declares.

A card holds intent, never the state of the code, which can change while it waits; see [`DESIGN.md`](../DESIGN.md). Every delivery reads the card through `scout-card`: its title, body, comments, labels, relations, and the branch name the board gives it. The title and body are the story text. Each run takes a digest of that text, so a rerun can tell when the card changed.

## Story, for `deliver-story`

A non-simple story, delivered through a spec.

| Part                   | Required | What the run does with it                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| ---------------------- | -------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `Deliverable` label    | yes      | The only gate. A card without it stops the run with a comment that says to run `shape`. No agent checks the rest of this contract, so the label means `shape` has.                                                                                                                                                                                                                                                                                                                                                                                                                  |
| Title                  | yes      | Names the outcome. It also names the spec folder, `docs/specs/<id>-<title slug>/`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| Summary and why        | yes      | Who benefits and why it matters. Designers, advisors, and every `judge` read the whole issue as the reason behind the work.                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| Scope and out of scope | yes      | What the change covers and what it must not touch. `lens-scope` fails a spec that adds or drops scope, and `qa` flags changes no criterion calls for.                                                                                                                                                                                                                                                                                                                                                                                                                               |
| Acceptance criteria    | yes      | One behavior each, in the product's own terms, that passes or fails with nothing in between. Each is checkable the way `TESTING.md` says to check its category, within what that category permits. Each is copied word for word into `validate.json`, filed under a `TESTING.md` category, and becomes a test and a validation path. A criterion no category can check is `uncategorized`, which `TESTING.md`'s Uncategorized setting usually holds as a draft. A criterion that names an implementation leaves the spec no choice, and one that can't be observed can't be proved. |
| No implementation      | yes      | The issue says why and what, never how. The how phase decides how, and the spec records it. A constraint the product or user truly imposes, such as a platform or a compatibility guarantee, is part of the what.                                                                                                                                                                                                                                                                                                                                                                   |
| No open decisions      | yes      | Every choice that changes what the story delivers or whom it serves is settled on the card. The run makes every how choice itself, but it never changes what the issue asks for, so a what question left open reaches the PR as a draft.                                                                                                                                                                                                                                                                                                                                            |
| Assumptions            | when any | What `shape` settled without asking, stated so a reader can object before delivery.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| References             | when any | Links and prior cards. Never code locations or a description of how the code behaves now: those go stale while the card waits, so every run reads the code itself.                                                                                                                                                                                                                                                                                                                                                                                                                  |
| Dependencies           | when any | Linear blocking relations, as `docs/BOARD.md` declares. One story is one issue and one PR.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |

## Trivial story, for `deliver-trivial`

A small change with no spec. A prompt is enough: the run files a card from it word for word. A card from `shape` works too.

- **What to change**, stated so that a test can check it. The first test states the new behavior, and the whole story is validated as one criterion under the `TESTING.md` category that covers it.
- Anything it leaves open beyond a trivial choice, such as a name or an obvious default, keeps the PR a draft and is listed for you to settle.

## Bug, for `deliver-bugfix`

A Bug card or a report. A report gets a Bug card filed from it word for word.

- **Observed:** what happens, with any error or output.
- **Expected:** what should happen instead. Without it, the reproduction decides from the code's evident contract, such as a function's name, docs, and tests, and says so.
- **Where or how:** the steps or input that show it, as a user meets it, as far as known. The scouts and the reproduction start from these.

The run's reproduction is the evidence; the card doesn't need to hold one.

## Question, for `deliver-spike`

A spike card or a prompt. A prompt gets a spike card filed from it word for word.

- **The question**, bounded: what would count as an answer. `lens-question` splits it into parts and checks each has an answer or is named as unknown.
- **Conditions**, when they matter: the environment, versions, or scale an answer must hold for. Anything left open becomes an assumption the findings state.
