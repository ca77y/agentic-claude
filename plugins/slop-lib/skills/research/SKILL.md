Investigate the requested question and persist reusable evidence and synthesis. Give a cited answer supported by the saved artifacts, including material uncertainty. Research does not authorize product decisions, tickets, implementation, or external publication.

## Ledger ownership

On every invocation, open or create the run's durable ledger using the ledger procedure at `${CLAUDE_SKILL_DIR}/references/ledger.md` and the template at `${CLAUDE_SKILL_DIR}/assets/ledger.md` before production or delegation. The main agent is its sole writer, including for trivial work and runs without subagents. Record returned agent IDs, assignments and progress; update before dispatch and waits, immediately after dispatch, on results and gate/failure changes, and before handoff or the final response. Reuse the ledger on resume and across entry points within the same run, preserving its failure history. A separate later user request gets a new run ledger; prior run history remains context, not its attempt count. Link the ledger in the final response.

## Context and source authority

Read the question, relevant existing knowledge, and `library/_meta/librarian.md` before library work. Follow project metadata, templates, and authoring conventions. If the library is missing, report that bootstrap is needed before library writes; authorized investigation and preparation may continue, but persistence remains incomplete. If existing conventions conflict with owner or sole-scribe integration, report the specific binding conflict and request an authorized convention update; do not silently override it. Ordinary research consumes conventions without loading bootstrap instructions or running setup. Bootstrap is separately invocable when requested.

Use the configured source provider named by the project's instructions or library conventions. If the required provider is unavailable, report the limitation rather than substitute another provider. Failed retrieval does not establish that a capability or fact does not exist. For empty, failed, thin, or conflicting retrieval, read `${CLAUDE_SKILL_DIR}/references/retrieval.md`.

## Production and completion

Frame bounded questions and use existing evidence to avoid repeating supported work. Optionally delegate existing knowledge to `slop-lib:librarian`, new source questions to `slop-lib:researcher`, and research-spec drafting or evidence persistence to `slop-lib:scribe`. Researchers return findings and provenance without writing library files. Assign raw-note scribes exclusive paths. The main agent or one designated scribe is the sole active writer of synthesis, index, taxonomy, and log; never both concurrently. Wait for outstanding raw-note writers and complete deferred shared metadata before final validation. These production options form no mandatory role chain; work directly when an optional role is unavailable. A source batch does not require one agent per source.

Before persisting sources or synthesis, read `${CLAUDE_SKILL_DIR}/references/persistence.md`. Save source identity, access date, supporting passages, and provenance according to the library conventions. Cite consequential claims, distinguish retrieved facts from inference and product decisions, and retain material contradictions and uncertainty. Never overwrite raw source notes with synthesis.

For nontrivial changes to persisted content or library behavior, follow **written specification + fresh validation → implementation + fresh validation**. Nontrivial changes introduce or meaningfully alter contracts, data, architecture, configuration semantics, or operational procedures, or need material design decisions; file count does not decide. Before writing such changes, put a proportionate spec in the project's spec location, normally `docs/specs/`, with the question, scope, planned artifacts/conventions, constraints, acceptance criteria, and verification. It specifies evidence quality and coverage, not a predetermined research conclusion. A suitable existing spec still needs fresh validation of current fit. High-risk or materially uncertain designs need independent challenge in that gate. Retrieval and exploratory source gathering may inform the spec before the gate; do not implement persisted changes under that label.

Correct a blocking spec and obtain a new fresh verdict before implementation. Revise and revalidate a materially changed spec before the affected writes. Trivial edits with established intent and no material semantic impact may omit a written spec, but all validation remains fresh. Have a separate fresh validator assess final synthesis, raw evidence, affected metadata and links against acceptance. Correct findings and obtain a newly dispatched validator for revalidation. Spec passes do not reset failure counts, and later edits invalidate affected evidence.

Complete when the synthesis addresses the question to the degree available evidence supports, provenance is saved, and changed artifacts and affected links pass validation. A supported inconclusive conclusion can complete research. An investigation blocked by failed retrieval must be reported as blocked, not disguised as a completed answer. Return the cited answer, artifact links, verification scope/result, gaps, contradictions, and retrieval limits.

## Ownership and evidence

The main agent owns interpretation, decisions, production, integration, evidence, and the final response. Work directly or delegate bounded production when parallelism or context isolation helps. Use the configured production roles named here when helpful; delegation is optional. Work directly within scope if an optional production role is unavailable. Give each worker the bounded outcome, acceptance source, absolute project and allowed paths, concurrent owners, and problem identity with remaining attempt allocation. Give writers exclusive paths, identify concurrent owners, and require preservation of others' work. Continue a production worker holding useful context with `SendMessage` to its agent ID; its report arrives as a completion notification, so save the ledger and end the turn rather than polling. Never start another user session or scheduled task unless requested.

Infer the outcome from the request and conversation. Discussion alone does not authorize implementation. Compose explicitly requested outcomes in the same task, meeting each contract; completion of one does not authorize the next. Record scope changes and decisions; preserve failure history for continuations of the same run, and keep a separate later request’s attempt count independent. Ask a focused question only when a missing decision prevents sound progress; continue independent authorized work.

Tie completion evidence to its acceptance source, exact artifact or candidate revision, observation/check, and result. A content digest or an identified unchanged snapshot can identify uncommitted work. Keep this evidence in the mandatory ledger, linking larger artifacts instead of duplicating them. Later edits invalidate affected evidence. Missing, failed, and unrunnable checks remain visible and are never passes.

## Fresh validation

Delegate **every audit and validation** to a fresh `Agent` dispatch of `slop-lib:clerk` — never a `SendMessage` continuation or a fork. This includes specification gates, correctness and acceptance review, tests, mechanical validators, documentation, citation, link and formatting checks, optional checks, and revalidation. There is no small-edit or documentation exception. Ordinary reading and diagnosis for production may be done directly; evidence used to establish completion belongs to a validator. Do not self-certify or rename checks to avoid delegation.

Fresh means no prior participation in authoring, implementation, or validation of the work examined. Never reuse an implementer, a spec validator for implementation acceptance, or an earlier validator after corrections; dispatch a new agent, never `SendMessage`, for every new verdict. Supply the user requirements and authority, absolute project path and relevant rules, exact candidate and spec identity where applicable, raw evidence, applicable checks, and bounded validation scope. Previous findings identify rechecks, not the answer. The validator reports without editing the candidate. Integrate findings and corrections without overriding a failed gate. If the configured validator is unavailable, preserve prepared work and report the unmet condition; do not substitute a generic agent or validate in the main agent. This plugin ships the validator role.

## Model selection

For each delegated task select a model — `haiku`, `sonnet`, or `opus`, passed as `model:` on the `Agent` dispatch. Consider responsibility, ambiguity, context needs, consequences of error, reliable capability guidance, and observed outcomes; role identity does not determine the model. Keep a brief selection rationale in the brief. Between two plausible capability tiers, try the lower capable tier first; clearly demanding work can start stronger. Do not reduce validation scope, invent availability, or silently substitute an unsupported model. Effort is not a dispatch parameter; agent definitions carry no fixed model, so dispatch selections apply.

After failure, use evidence to improve the approach or select greater capability within the remaining budget. A model change alone is not a new solution. The main agent remains on its session's model; it can delegate a bounded harder problem, but cannot promise to switch itself.

## Three-attempt stop gate

Track at most **three failed solution attempts for the same unresolved problem within the current run across the main agent and all workers**. An attempt is an approach carried far enough to evaluate acceptance, including an approach that proves unworkable before producing a candidate. Multiple edits or individual checks in one candidate evaluation are one attempt; a corrective approach after an evaluated failure is the next. Exploration and baseline reproduction do not each consume attempts. Evaluated specification and implementation failures share the count; a passed spec gate does not reset it.

The budget belongs to one run from the initiating user prompt through resolution of that request, not to the lifetime of a PR, branch, artifact, or conversation. A separate later request, such as reviewing PR comments, starts a new run with its own budget even on the same PR. Reading comments, discovering defects, and reporting findings are not failed solution attempts. Count only evaluated solution approaches undertaken in the current run.

Within that run, the count follows the unresolved outcome across changed errors, hypotheses, models, agents, gates, entry points, checkouts, interruptions, and conversation turns. A continuation or resumption of unfinished work retains the count, including after a stop; merely invoking another skill or asking to continue does not grant extra attempts. Close a problem on verified resolution; restore its history if evidence within the same run shows resolution never held. Independent problems may have separate counts, but reaching three on any problem stops the entire run, including background work.

Give delegated solution work the problem identity and remaining budget, and require all evaluated internal failures to be reported without hidden repair loops. Prefer one owner for successive attempts. Reserve an attempt slot for each parallel alternative solution before dispatch; evidence gathering alone does not consume solution slots. The main agent aggregates failures and escalation decisions. Recover the existing ledger before resuming; preserve failure history there throughout the run, never only in worker handles or files subject to scratch cleanup. If durable storage is unavailable, return the ledger and the unmet persistence condition instead of silently resuming without history.

On the third failure, stop active workers and execution: no fourth attempt, further escalation, or publication as complete. Saving artifacts and recovery state is permitted. Return the unresolved outcome and blocking evidence, all three approaches with models where applicable and why each failed, current candidate and useful completed work, and the specific decision, information, access, or explicit additional attempt authorization needed. Return earlier if essential access, authority, information, or a plausible next approach is absent. Further attempts require explicit user authorization recorded alongside, never replacing, the history. These instructions define workflow behavior, not a hard tool-level runtime counter.
