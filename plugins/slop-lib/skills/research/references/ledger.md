# Orchestrator ledger

Read on every invocation, before production or delegation. The main agent maintains one durable ledger for the prompt-to-resolution run, including trivial work, answer-only work, bootstrap, and installation. Leaves report progress and failures; they never write the shared ledger. Initial context reading and ledger/spec preparation need no recursive specification gate.

## Open and own the ledger

Resolve the project's temp folder from its forge declaration (normally `docs/FORGE.md`). Resolve relative paths against the project root; preserve absolute paths. If the declaration or temp-folder setting is absent, use `.tmp/` under the project root without requiring bootstrap or the engineering plugin. Store project ledgers in `<temp-folder>/ledgers/`. Use the actual project root, never the installed skill's working directory. For work without a project, use `~/.claude/ledgers/`.

Follow a supplied ledger path or a ledger reference in the task, spec, or PR when resuming existing work. Before creating a new ledger in a Git project, enumerate all registered checkouts with `git worktree list --porcelain`. For each checkout, resolve its own forge-configured/default temp folder and search its `ledgers/` directory and legacy `docs/ledgers/` directory. Deduplicate absolute directories. Without Git, search the current project's configured/default and legacy directories; for projectless work, search the personal directory. Match the initiating request/run as well as project identity, outcome, and acceptance source, separately from the checkout and entry point. The same PR or artifact alone is not a run match. Reuse a same-run match wherever found, subject to ownership below; link earlier runs as context without importing their attempt counts. A missing ledger directory is normal; an unavailable listed worktree, unreadable candidate directory, failed enumeration, or inaccessible explicit ledger reference is a recovery gap, not evidence that no ledger exists. Complete discovery before creating new history.

Reuse the matching ledger across skills and turns that continue the same unfinished request. A separate later user request, including a PR comment review, starts a new run and ledger with zero failed attempts; preserve earlier ledgers as history. For a new run, or when no existing record matches the current run, copy [the template](../assets/ledger.md) into that directory as `<run-id>.md`, using a supplied run ID or a unique date-and-outcome ID. Record its absolute path and available owner/task handle. Missing runtime IDs are explicitly unavailable, never invented. If records conflict or failure history is incomplete, report the recovery gap before more production.

The current task is the sole writer. A different task must obtain an explicit release/handoff from the owner or user before claiming an active ledger. The outgoing owner saves state, releases ownership, and records the destination and next owner. The incoming owner confirms the previous owner has stopped writing, records the transfer, and then resumes. Uncertain ownership blocks production; a resumed current task retains ownership.

Before creating or updating a ledger inside a Git worktree, verify that its destination is untracked and ignored with `git ls-files` and `git check-ignore` from that worktree. If it is not ignored, resolve the local exclude file using `git rev-parse --git-path info/exclude` (resolve relative output against the command's working directory). Preserve existing content and append an anchored rule for only the ledger directory relative to the worktree root, such as `/.tmp/ledgers/`. Escape Git ignore pattern metacharacters so the path is literal, including for custom paths; preserve a separating newline. Recheck the actual ledger path with `git check-ignore` before writing. Tracked destinations, ineffective exclusions, or inability to save the rule block ledger writes; report the unmet condition rather than changing the configured destination. This local bookkeeping needs no bootstrap and does not authorize editing tracked `.gitignore`, removing tracked files, or forced staging. Non-Git and outside-worktree destinations need no Git ignore rule.

Keep ledgers outside the research library and installed plugin source/cache. Although stored in the temp folder, ledgers and required evidence are retained workflow state: exclude them from scratch cleanup and preserve them across resumptions and completion. Local operational bookkeeping does not authorize library content changes, commits, or external writes. If persistence is explicitly forbidden or unavailable, return the ledger content and unmet persistence condition in the conversation; do not silently continue without the required durable record.

## Maintain progress and subagent identities

Fill the template with the acceptance source, authority/endpoint, spec and candidate identities, current phase, completed/pending/blocked work, artifacts, decisions, evidence, and next action. Use `none`, `not applicable`, or `unavailable` explicitly instead of pretending a spec, worker, or result exists.

- Before each `Agent` dispatch, record the assignment, configured role, allowed paths, problem identity, model and selection rationale, and any reserved solution slot.
- Immediately after dispatch, save the returned agent ID when the dispatch produced one; a synchronous dispatch may return only its report, so mark the ID unavailable rather than inventing one. Failed dispatches remain recorded without fabricated IDs.
- Give each worker the absolute ledger path as read-only context, require meaningful progress, results and all evaluated failures, and reserve ledger writes to the orchestrator.
- Update assignments/status before a `SendMessage` continuation, and progress, results, evidence and next actions when worker updates arrive. Keep old worker records when replacing a worker.
- Save current state before ending the turn to await a completion notification, or before another wait, after every gate verdict/evaluated failure, and before the final response, planned interruption, handoff or stop. On an unexpected interruption, reconcile the last saved state before resuming.

Keep the current summary concise and retain gate and failure history. Link evidence to its acceptance source, exact spec/candidate revision, observation/check, and pass/fail/unverified result. Mark affected evidence stale after product edits. Ledger-only status updates do not change the validated product candidate or require recursive validation. Record only evaluated solution failures from this run across all workers and gates under the same unresolved problem; reading comments and discovering or reporting defects do not consume attempts; maintain reserved slots, remaining budget and any explicit additional-attempt authorization. Within the same run, a passed gate, replacement worker, changed entry point, or request to continue never resets failures.

## Resume and close

When continuing the same run, read its existing ledger before another solution attempt. Reconcile its progress, reservations and worker statuses with available runtime state and actual artifacts. A stored ID is a handle, not proof that its worker is still live or that its work passed. Mark stale/unavailable workers honestly; preserve their IDs and recover their artifacts/results before deciding what needs replacement. Unknown attempt history is a recovery gap, not zero. A fresh validation assignment always gets a newly dispatched validator.

At the third failed attempt for any unresolved problem, stop the entire run and active workers using `TaskStop` where available, save their actual statuses and useful work, and return the blocking evidence and required decision or explicit additional-attempt authorization. Record any inability to stop a worker; do not report it as stopped.

Before checkout/task handoff or worktree removal, carry the ledger and its required evidence to the durable destination, pass the absolute path, and complete the ownership transfer. Do not assume an untracked file travels with git state. Retain the ledger after completion, record the authorized endpoint reached or the unmet condition and next action, and link it in the final response. Completion never deletes failure history; later requests keep independent counts even if new evidence challenges an earlier result.
